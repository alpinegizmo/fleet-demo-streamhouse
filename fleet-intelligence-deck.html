Fleet Telemetry Demo
The problem

Fleet data arrives.
Insight doesn't.

  • Systems don't talk to each other.Telemetry, weather, traffic, and parcel data sit in separate systems with no shared, real-time view.
  • Maintenance is reactive.An engine issue is caught at breakdown, not at the moment it started trending wrong.
  • Safety review happens weekly.A harsh-braking pattern gets flagged in Friday's report — five days after it mattered.
  • Dispatch reacts by phone call.A route gets manually rerouted hours after a delay has already cascaded through the day.
By the time a report says "this vehicle needs attention," it needed attention yesterday.
Why real-time

Batch tells you what happened.
Streaming tells you what's happening.

Batch ETL
Nightly job, morning report
Data lands in a warehouse on a schedule. By the time anyone queries it, the moment it describes is already hours or days old.
VS
Event streaming
Every reading is an event
The instant a vehicle reports, that's a record on the stream — available to every consumer immediately, not on a schedule.

And because each business domain reads the same stream independently — safety, delivery, and maintenance don't wait on each other, or on a shared database, to react.

The building blocks

One durable log.
Every team builds on it independently.

  • Apache KafkaThe durable event log every downstream system reads from — no producer coupled to any one consumer.
  • Flink SQLStream processing written as SQL — not a bespoke consumer application per team, per language. The table definitions double as the schema contract.
  • Model calls inside the streamML_PREDICT calls a local model (Ollama, OpenAI-compatible) from a Flink SQL statement — no separate inference service to build, deploy, or scale.
  • Apache IcebergFlink also commits the derived streams as open tables, so analytics engines (DuckDB here) query the same data without a separate pipeline.
The stream processor isn't just where data lands — it's where the business logic and the AI inference actually run.
The solution

One raw stream. Three domains.
Real AI at the end of each.

Raw vehicle telemetry — plus weather, traffic, and parcel-volume context — feeds a continuous Flink SQL pipeline that derives three independent business events: safety, delivery, and maintenance. Each event is handed to a local LLM, from inside the Flink job, for a generated recommendation, published back to Kafka as its own topic — readable by a dashboard, by an agent over MCP (Claude Code, VS Code Copilot), or as an Iceberg table from DuckDB. All of it runs on a laptop.

The demo

What you'll see

  1. Open the Fleet Intelligence Console12 vehicles on a real Melbourne metro map, three business dashboards, live business-impact KPIs — every number read from the real pipeline.
  2. Inject an engine spikeA real record goes into Kafka; Flink derives a maintenance alert and the local model's recommendation is on screen about a second later.
  3. Open Behind the ScenesThe pipeline animated from real events: topic arrivals, Flink jobs, Iceberg commits, agent queries.
  4. Ask the live dataFrom the console's chat, or Claude Code / VS Code Copilot over MCP — the agent answers by running SQL over the same live topics the dashboard reads.
  5. Query the lakehousemake duckdb: the same events and recommendations as Iceberg tables, about 30 seconds behind the stream.
Run it yourself

Zero to AI recommendation
in three commands

# once: a local model server (uses the Mac's GPU)
brew install ollama && brew services start ollama
make model      # ollama pull qwen2.5:3b
# Kafka, Flink, Iceberg, the app — all in Docker
make up
open http://localhost:8787
